### 第一层:模型不听话?—— 不,是指令挂错了节点

**现象**:`agent` 节点写了「结尾加喵~」,最终回答没有。

**排查**:单独把那句 system prompt 拿出来测,同一个问题跑 3 次,**3/3 都加了喵~**。模型没问题。

**根因**:最终回答不是 `agent` 产出的,是 **`write_report` 节点**产出的。那是**另一间办公室**,
它**从零重构了上下文**,压根看不到 `agent` 的 prompt。

**解法**:跨节点的要求必须走 **state**,再由目标节点**主动读出来**。

**这一层的认知修正**:

> **系统提示词不是"全局设置",是"单次调用的参数"。**
> LangGraph 里没有"整张图的 system prompt"这种东西。
> 节点之间**只共享 state,不共享 prompt**。

---

### 第二层:那 state 到底是什么?—— 白板,不是历史

**我原来的理解**:state 像"过去的状态记录",是一条流水账。

**修正**:state 是一块**共享白板**。

- `messages` 那栏用 `Annotated[list, operator.add]` → **追加**,所以看起来像流水账
- 但那是**一栏的合并规则**,不是 state 的本质
- 另一栏 `question: str` 就是**一直贴在白板上的便签**,谁进门都能读

**一句话**:**指令跟着节点走(局部生效);要求跟着 state 走(谁需要谁读)。**

**具体到操作,分两步,缺一不可**:
1. **运输**:把要求作为 state 的一栏摆上白板
2. **消费**:目标节点**主动读**这栏,写进自己的 prompt

只有①没有②,等于没写。

### 第三层(最狠):为什么 system 一个字都没到模型?

换了本地代理后,system prompt **完全失效**。挖出两层根因。

**怎么证的(关键手法——两个探针)**:

- **行为探针**:system 里写「必须以『菠萝蜜多』开头」→ **0/4 遵守**
- **不依赖模型行为的探针**:往 system 塞 900 字符,看 `prompt_tokens` 涨不涨 → **58 → 58,一个 token 都没涨**

第二个探针是关键。**它不依赖"模型表现",直接看"内容有没有到"。**

**根因**:那个代理工具**默认会用自有提示词"替换"客户端的 system 消息**
(它文档里写着,是为了规避上游内容审核的逐字误杀)。

**顺带发现**:孤儿 `ToolMessage`(没有配对的 `AIMessage.tool_calls`)内容会被**静默丢弃**。

**失败方式全是「不报错、但也不干活」。**

**解法**:换成标准端点,system 恢复正常(对照组:规则放 system → 1/1 遵守)。

**这一层学到的**:

1. **链路里每一层都可能静默改你的请求。**
   要验证"内容到底到没到",用**不依赖模型行为**的探针(如 token 数),别只看输出像不像。
2. **`ToolMessage` 有配对契约**——必须紧跟带 `tool_calls` 的 `AIMessage`。
   所以"只留材料、丢掉动作"时,材料必须**降级成纯文本、重包成 `HumanMessage`**,不能留成 `ToolMessage`。
   —— 两条路都不通:留配对 → 工具调用示范诱发 DSML;丢 AI → 孤儿 → 内容丢。**唯一出路是降级成裸文本。**

**顺带炸出一条**:换了标准端点后,`load_dotenv()` 默认**不覆盖**已存在的环境变量。
我机器上 `ANTHROPIC_API_KEY` 已被设成**空字符串**,把 `.env` 里的真 key 挡掉了 → 认证失败。
解法:`load_dotenv(override=True)`。

### 第四层:BaseModel 是什么?—— 数据模具,不是执行体

**我原来的理解**:`class Plan(BaseModel)` 是"定义模型的执行体"。

**修正**:它**不执行任何东西**。它只是一份**能编译成 JSON Schema 的规格书**。

```
你写的类体
    │ ModelMetaclass 扫描注解
    ▼
model_fields   (字段名 + annotation + description + required)
    │ model_json_schema() 翻译
    ▼
JSON Schema   ({"properties": {...}, "required": [...]})
    │ LangChain 包成工具定义
    ▼
发给模型的 tools 数组
    │ 模型按 schema 调这个"工具",把数据塞进 arguments
    ▼
LangChain 用同一张表反向解析 → Plan 对象
```

**逐字搬运**:字段名 → `properties` 的 key;`list[str]` → `"type":"array"` + `"items":{"type":"string"}`;
`Field(description=...)` → `"description"`(模型看得到,**又是一条提示词**)。

**三个必须记住的**:
1. `= 默认值` 决定"必填还是选填",也决定 schema 的 `required`
2. 类型是"宽容转换":`"20"` → `20`;转不了才报错
3. `Field` 的参数**一进两处**:schema(模型看)+ 校验器(代码查)

**和 `TypedDict` 的分工**:
- `TypedDict` = **标注**(不校验)。给 LangGraph 描述 state 形状用,轻量
- `BaseModel` = **契约**(真校验)。接模型输出、保证下游数据形状时用

**一句话**:**你要的不是一段话,是一个列表;而模型只会给话。`BaseModel` 是那道转换器。**

### 第五层:结构化输出会**静默失败**

`with_structured_output(Plan)` 不是万能的。实测撞到:
模型把整个数组**序列化成了一个字符串**(`'["a","b"]'`),`parsed` 返回 **`None`**。

而我代码里 `plan.topics` 没判空 → **直接 AttributeError**。

**解法**:`if plan is None:` 降级处理。

**这一层学到的**:它把成功率从 1/3 拉高到接近 100%,**但不是 100%**。
**凡是吃它输出的代码都得判空。**

## 另外几个小的

- **`enumerate(列表, 1)` 的 `1`** 是"标签从几开始",**不改个数、不改顺序**。
  判断标准:`i` 拿去**显示编号** → 从 1;`i` 拿去**当数组下标取值** → 必须从 0(否则错位/越界)。
- **`invoke` 的初始 state**:有节点会写的栏 → 初始值可选(但传了是**安全网**,
  防止"没人写但有人读"时 `KeyError`);只读不写的栏(如 `question`)→ **必须传**。
- **"让大模型拆任务"≠"它自己知道拆什么"**。模型是无状态函数,**它只知道你这次发给它的东西**。
  `HumanMessage(content=state["question"])` 是把题目**递进去**;`question` 的值在入口 `invoke` 处赋。
- **配置该走哪**:`topic`(每次变)走 **state**;api_key / 模型 / 工具(不变)走 **模块级全局**。
  但"写死在全局"有三个后果 → 这是 **v0.4 `config_schema`** 要解决的。

## v0.3 的 Send / Command 代码理解(补记,记入 2026-10-14)

回到 `0.3demo.py`,把 `Send` 版里主管派工、state 更新和并行结果汇总的关系补清楚了。

### `Command` 不是只负责跳转

`Command(goto=..., update=...)` 一次表达两件事:

- `goto` 负责路由。主管生成多个子问题后,`goto` 中每个 `Send("researcher", {...})` 派发一路研究员;`Send` 字典是那一路**研究员子图**的输入(`topic`、`messages`、`rounds`)。
- `update` 负责更新**当前节点所属图**的 state。`supervisor` 在主图里,因此 `update={"topics": topics}` 把完整计划写入主图的 `State`,不是写进每个研究员的 state。

主图和研究员子图各有一块白板:`State` 放 `question/topics/findings/report`;`ResearcherState` 放 `messages/topic/rounds/findings`。同名的 `findings` 是两张白板上各自的栏位,不是整张图共享一个字典。

### 为什么还 update `topics`

`Send` 里的每个 `topic` 已经足够派发任务。`update` 不负责派工,只是把完整拆题清单留在主图 state,方便最终检查或供后续节点使用。当前 demo 没有后续节点读取主图的 `topics`,所以去掉这项 update 不会改变 researcher 执行或最终报告;只是最终 state 不再保留这份计划。

### `findings` 的列表形状与 reducer

- `ResearcherState.findings` 改成列表,因为 `compress` 返回 `{"findings": [text_of(r)]}`。列表是子图输出的形状,能和父图的 `findings` 对齐。
- 父图有多个 `Send` 研究员并行返回 `findings`,父图的 `Annotated[list, operator.add]` 负责把这些列表拼起来。没有 reducer,同一轮的并发写入会发生 state 更新冲突。
- 当前每个研究员子图里只有 `compress` 写一次 `findings`;所以**子图这栏的 reducer 不是仅因使用 `Send` 就必需**,更多是沿用相同合并语义/为多写入留余地。真正必须处理并行汇总的是父图的 reducer。

### 串行时为什么看起来不需要 reducer

串行版本可以由一个汇总节点在 Python 局部列表里逐个收集结果,最后只向主图写回一次完整 `findings`;这样 reducer 不必负责收集。

但“串行”本身不等于自动累积:如果多个图节点仍先后向同一个 state 字段写入,而字段没有 reducer,后一次写入可能覆盖前一次。关键在于**谁负责汇总,以及主图实际收到几次 state 更新**,不只是任务是否同时运行。

### 这次补记的边界

现在理解了代码语义,但这不等于完成并发实验。`Send` 的 `max_concurrency` 实际峰值、耗时和成本是否与 `asyncio.gather` 的手动限流相当,仍待运行探针确认;继续跟踪 `IMPROVEMENTS.md` 第 3 条。
