### 3. 并行为什么不用官方 Send?

上游当前版本用 `asyncio.gather` 做并行研究;练习代码也做了一个 `Send` 版本。`Send` 把动态派发交给 LangGraph 调度,练习里通过运行配置传入 `max_concurrency=1`。

**问题**:`Send` 的 `max_concurrency` 对研究员子图的实际并发峰值控制到什么程度?与 `asyncio.gather` 的 semaphore/worker pool 相比,控制粒度和成本可见性有什么差别?

**状态**:已理解代码层面的职责——`Send` 派发任务,主图 `findings` reducer 汇总并行返回值;`Command.update` 更新当前图的 state。并发峰值、耗时和成本差异仍需实测,不能仅凭代码结构下结论。

**这个值得实测一次** —— 它同时是个**好的面试话题**:框架调度与手动限流各自的控制边界是什么,你选哪个、为什么。

### 7. 结构化输出没有判空(2026-10-14,已撞到)

`with_structured_output(Plan)` 实测会**静默返回 `None`**(模型把数组序列化成了字符串),
而 `plan.topics` 直接 `AttributeError`。

**问题**:凡是吃结构化输出的地方,是不是都该包一层"判空 + 降级"?
能不能做成一个统一的 helper,而不是每处手写 `if plan is None`?

**为什么值得做**:**失败方式是静默的**——不判空就等它某天在生产上崩。

### 8. 配置写死在模块级全局(2026-10-14)

现在 `model` / `api_key` / `tools` / `MAX_ROUNDS` 全是模块级全局,三个研究员共用同一个 model 对象。

**问题**:想给"主管用贵模型、研究员用便宜模型"必须改代码。
想"不改一行代码只改配置换模型"更不可能。

**这就是 v0.4 的主题**(`Configuration` + `config_schema`)——不是新问题,是 v0.4 要解的那个。
记在这里是为了**记住它的痛点是怎么冒出来的**:不是"规划里说要学",是**真的被绊了一下**。
