### 4. 推理模型的成本陷阱

代理返回的元数据里:`"only_reasoning": true`,`"reasoning_default_effort": "high"`。

**推理模型**:回答前先在"草稿纸"上算一遍。数学逻辑更准,但**慢,而且草稿也按 token 收费**。

这个 agent 一次运行会调用模型**几十上百次**,推理模型的成本会被放大。

**可调的旋钮**:`reasoning_supported_efforts: ["low","high","max"]`。

**悬着的问题**:用便宜模型做"主管"节点会不会出问题?主管做的全是判断题("信息够了吗")。便宜模型可能**在信息不够时说"够了"**,然后收工——你拿到一份**看起来像那么回事、实际很浅**的报告,而且**不报错**。

### 两个只有跑起来才看得见的点

**① `question` 还在——尽管没有任何节点返回过它。**

`answer` 基本就是 `points` 的换词重写。**第二个节点没干实事,它只是复述了第一个节点的输出。**

## 发现:docstring 就是提示词(自己抓到的)

跑 v0.2 时把请求体打出来看,发现:

```json
{"tools": [{"type": "function", "function": {
   "name": "search",
   "description": "搜索资料。返回与关键词相关的资料片段。",
   "parameters": {"properties": {"query": {"type": "string"}}, "required": ["query"]}
}}]}
```

**`@tool` 做了三件事**:

| 写的东西 | 变成 |
|---|---|
| 函数名 `search` | `"name"` |
| **docstring** | **`"description"`** ← 模型靠这个决定调不调 |
| 类型标注 `query: str` | `"parameters"` 的 JSON Schema |

### 两个推论

**① 工具描述和 system prompt 是同一类东西——都是给模型的指令。**

所以写法也该一样:说**什么时候用**,不是说明**它是什么**。

对照:

- 我写的:`"搜索资料。返回与关键词相关的资料片段。"` ← 说的是**是什么**
- 上游 `think_tool` 的:`"When to use: - After receiving search results: What key information did I find?..."` ← 说的是**什么时候用**

**上游那段不是文档,是给模型的行为指令。**

**② 这解释了 v0.2 为什么不收敛。**

我的描述里既没说"什么时候该搜",也没说"够了就别搜"。唯一的指令是 system prompt 里那句"需要资料时调用 search"——**只说了要用,没说够了要停**。

**于是它一直搜,直到被 `MAX_ROUNDS` 掐断。**

### ③ 而且这段每次都发

`tools` 是请求体的一部分,**每循环一轮就重发一次**。现在只有 1 个工具、20 字描述,无所谓;加到 10 个工具、每个 100 字,每轮多几百 token × 循环几十轮。

**"工具要少而精"是成本问题,不是风格问题。**

### 待做实验(只改 docstring,别的都不动)

把 `search` 的描述改成"说什么时候用 + 什么时候停",看同一问题的**循环轮数**和**能否自己收敛**。

**如果行为变了,就证明:工具描述是提示词,提示词决定行为。** 这比 ReAct 的图结构本身值钱。

## v0.2 收尾:三个真实的坑

### 1. 「研究完成」不等于「有答案」

加了 `ResearchComplete` 工具后,循环终于能自己收手了:

```
[agent] 第 3 轮 | 想调: ['ResearchComplete']
[路由] 模型主动说完成了 -> END
最终回答: (空)
```

**但最终回答是空的。** 因为:

- `ResearchComplete` 的参数是 `{}`——**它没有地方装答案**
- 模型调它的时候,`content` 可空可非空(实测两种都出现过)
- **它是"我搜够了"的信号,不是交付物**

**根本结论:「研究完成」和「写出报告」是两件事,需要两次独立的模型调用。**

上游正是这么做的:主管节点只负责收集 `notes`,交给独立的 `final_report_generation` 节点写报告(`deep_researcher.py:607-697`),而且专门配了 `final_report_model`。

**判断标准**:参数是"指令"(短、结构化)→ 工具;参数是"交付物"(长、给用户看)→ 节点。

### 2. 写报告节点会把工具调用语法漏进正文

加了 `write_report` 节点后,输出变成了这样:

```
<||DSML|| calls>
<||DSML|| invoke name="search">
<||DSML|| parameter name="query" string="true">LangGraph 循环 分支</||DSML|| parameter>
</||DSML|| invoke>
```

**模型把"工具调用语法"当成普通文字吐出来了。** DeepSeek 内部用 `DSML` 标记表示工具调用,正常应被解析成结构化的 `tool_calls`——这次没解析,原样漏进 `content`。

**原因:上下文污染。** `write_report` 拿到的是全部历史,里面全是"怎么调工具"的示范:

```
[1] AI  tool_calls=['search','search']
[4] AI  tool_calls=['search','search','search']
[8] AI  tool_calls=['ResearchComplete']
```

**大模型有很强的模仿本能**——看到前面全是工具调用,就接着写了一个,而不是写文章。

**更具体**:撞到轮数上限时**特别容易**发作。因为被强行掐断时,最后一条消息正处在"正在调工具"的状态,那个状态直接进了写报告的上下文。

**修法**:
1. 用 `get_buffer_string()` 把历史**拍平成纯文本**再喂(工具调用变成文字描述,不再是可模仿的格式)
2. 提示词里**明确禁止**("直接输出正文,不要调用任何工具")

**上游天然避开这个**:`final_report_generation` 拿到的是 `"\n".join(notes)`——**纯字符串,不是消息历史**。过程记录里的工具调用格式,根本不进写报告的上下文。

### 3. 一条值得记住的经验

> **凡是"从循环切到产出"的那一步,都要做上下文清理。**

因为循环里是**动作**(调工具),产出阶段要的是**材料**。把动作记录直接倒给产出模型,它就会接着做动作。
